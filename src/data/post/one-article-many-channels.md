一篇文章准备发到多个平台时，我最担心的是版本越来越多，最后自己也分不清：哪一份是原稿？哪个标题已经改过？发现一个错误，应该去哪里修正？

所以，我想先建立一套能长期维护的流程：**完整原稿 → 官网发布 → 平台改写 → 发布记录 → 反馈与修订**。先让内容有一个清楚的源头，再增加传播入口。

## 第一步：把原稿写成能独立读懂的文章

我会先确定这篇文章要回答的一个问题，然后把背景、判断、具体做法和适用范围写完整。

原稿至少保留这些信息：标题、摘要、作者、发布日期、分类，以及需要引用的资料或相关链接。修订时补充更新时间；涉及事实的内容，尽量留下可以核对的依据。

写完之后，我会用三个问题检查它：

1. 读者看完开头，是否知道这篇文章与自己有什么关系？
2. 方法有没有具体到可以尝试，还是只有宽泛的观点？
3. 哪些内容已经做过，哪些只是下一步计划，是否说清楚了？

这一步决定文章本身有没有用。后面的改写与发布，都应当围绕它展开。

## 第二步：用 GitHub 维护原稿，让官网自动更新

本站已经采用 Markdown 管理文章：原稿放在 GitHub 仓库里，提交更新后，Cloudflare Pages 会自动构建网站。文章分类、列表和详情也会随构建更新。

对我来说，这解决了“原稿应该放在哪里”的问题。后续发现表达不清或需要补充时，先修改仓库中的文件，保留文章地址，再按发布记录检查其他版本。

这里自动完成的是官网更新。目前，各个平台的稿件改写和发布仍需要单独处理，我还没有接入跨平台自动发布。

## 第三步：围绕阅读场景改写，不只是换标题

不同形式的内容，需要重新组织表达。我的计划是从同一份原稿出发，按阅读需求准备版本：

- **完整长文**：保留背景、过程、例子与结论，适合深入理解。
- **问答稿**：先回答一个明确问题，再展开理由和做法。
- **图文卡片**：选出少量关键步骤，每张卡片表达一个意思。
- **短视频脚本**：把书面表达改成自然口语，围绕一个具体问题安排节奏。

例如，[《为什么我要搭建一个自己的个人网站》](/articles/a-place-for-my-work)的原稿讲述动机、内容结构和维护方式。改成问答稿时，可以围绕“独立开发者为什么需要个人网站”展开；改成卡片时，可以聚焦“作品、实验、文章分别放什么”。

这些是适配思路，尚未代表文章已经发布到对应平台。每个版本都应能独立读懂，同时保留作者信息；允许附链接时，再给出官网原文入口。

## 第四步：发布后留一份能追溯的记录

生成了一份稿件，还不等于完成发布。我准备为每篇文章维护简单的分发记录：

- 原稿地址与使用的版本或修订日期。
- 平台名称、平台稿标题，以及“待改写 / 待发布 / 已发布”的状态。
- 发布成功后的实际链接与日期。
- 值得回应的评论、需要纠正的内容，以及是否已同步修订。

记录的作用是减少遗漏。原稿有重要更正时，可以找到实际发布过的版本逐一检查；只有标题或表达调整时，也能判断是否值得同步。

## 第五步：把反馈带回原稿

我更想先观察内容是否帮助读者：他们反复追问哪个问题，哪一步不够清楚，哪些经验值得补充。阅读数据可以辅助判断，但不应成为修改文章的唯一依据。

如果后续观察搜索或 AI 引用表现，我也会记录具体问题、出现的来源链接和观察时间，再判断变化。多发几个平台，并不能直接当作“已经带来增长”的证据。

这套流程目前已经完成了官网与 GitHub 同步这一环。接下来，我会挑选一篇文章做平台适配、记录实际发布与反馈，并在[AI 企业增长的公开实验](/experiments/ai-business-growth)中更新进展。

对我来说，一篇文章的长期价值，来自后续不断补充的经验。先让它值得读，再让它更容易被找到、复用和维护。
